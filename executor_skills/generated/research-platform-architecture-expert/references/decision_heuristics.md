# Decision Heuristics

1. If the task involves frame the deliverable at the right level, then Identify the true work product, required structure, intended decision audience, non-goals, and minimum viable scope before drafting.
2. If the task involves define platform boundary and interaction model, then State the platform's physical form, user interaction model, responsibilities, excluded responsibilities, and tradeoffs between MVP and full system.
3. If the task involves govern data lineage, timing, missingness, and comparability, then Define data source, point-in-time availability, lineage, versioning, missingness, sample comparability, reconciliation, and blocking rules for unusable data.
4. If the task involves separate exploration, confirmation, and robustness, then Separate exploratory search from frozen confirmatory tests, define windows or scenarios, require failed-result logging, and specify quantitative success metrics.
5. If the task involves control outcome-driven selection, then Require locked configurations, timestamps, hashes or version ids, amendment logs, exploratory labels, complete disclosure, and escalation for conflicts.
6. If the task involves design audit, compliance, and external evidence packages, then Define audit artifacts, privacy controls, access roles, retention rules, external/internal package distinctions, and reviewer-facing summaries.
7. If the task involves phase work with resources and stop points, then Break the work into phases with deliverables, teams, success criteria, costs, permissions, and explicit stop/pause points.
8. If the task involves define success, downgrade, pause, and exit criteria, then Set quantitative and qualitative thresholds for success, downgrade, pause, escalation, and exit.
9. If the source task triggers `任务定位`, generalize the expert move: Identify the true task type, decision audience, and controlling objective before designing the response. Rationale: 该任务表面上是技术方案写作，但受众同时包括会计研究负责人、实证研究员、金融计量专家、数据工程团队和研究治理负责人。专家判断是：不能只写软件架构，也不能只写方法论；主线应定位为“方法评估与治理”，并围绕为什么需要平台、如何比较方法、如何保证公平、如何落地和如何审计展开。
10. If the source task triggers `核心矛盾识别`, generalize the expert move: Determine whether the task asks for a one-off analysis or a reusable evaluation and governance framework. Rationale: 团队真正担心的是测量方法选择不当导致研究结论不可靠，而不是要跑一次模拟并宣布某种方法最好。专家因此将平台价值定义为输出条件化结论：在什么条件下某方法更稳健、在什么条件下会失败，并要求所有比较过程可复现、可审计。
11. If the source task triggers `高优先级风险`, generalize the expert move: Surface the failure modes that would make the platform amplify bad research practice rather than correct it. Rationale: 会计研究中常见 proxy shopping 和显著性导向选择；模拟参数也可能被设计成偏向某一类方法。专家将“模拟偏向”和“结果导向选择”列为最高优先级风险，要求把预注册、全方法披露、多场景矩阵和尾部失败报告写入方案核心，而不是放在附录。
12. If the source task triggers `MVP判断`, generalize the expert move: Choose a minimum viable platform scope that can demonstrate value without overcommitting engineering resources. Rationale: 专家判断一开始建设完整 Web 平台和数据库接入成本过高，容易拖垮项目。最小可行版本应以模拟数据为主，比较几种基本方法，并交付构念定义、参数配置、运行流程和标准化报告模板；形态可以是可复现脚本集合加报告模板，而非一开始就做完整产品。
13. If the source task triggers `计量评估设计`, generalize the expert move: Define quantitative evaluation criteria and simulation dimensions that a statistical expert would accept. Rationale: 计量专家需要看到偏误、方差、MSE、尾部失败、小样本表现和极端情形，而不是笼统的优劣判断。专家会设置 true coefficient recovery 偏差、尾部失败率等指标，并要求模拟覆盖 loading 0.4 到 0.9、不同噪声水平、弱相关/负相关/块状相关、样本量 100 到 5000、结构系数 0 到 0.5，以及反映式与形成式两类数据生成过程。
14. If the source task triggers `数据工程约束`, generalize the expert move: Specify how empirical data ingestion, variable lineage, missing data, and sample comparability should be governed. Rationale: 数据工程团队会关心 Compustat、CRSP 等数据库变量变化、缺失值和不同方法样本不一致。专家要求主比较使用统一样本和统一缺失处理规则；任何方法专属缺失策略必须作为敏感性分析单独报告，并分解样本差异和方法差异。同时要记录变量血缘、软件版本、随机种子和配置快照。
15. If the source task triggers `预注册治理`, generalize the expert move: Design an auditable pre-registration mechanism that limits outcome-driven method selection. Rationale: 研究治理负责人需要知道研究员是否先看结果再选择方法。专家要求在评估前提交构念定义、候选方法、场景矩阵、主评估指标和样本构造规则，由系统生成时间戳和哈希锁定配置；后续修改必须作为 amendment 记录并披露是否发生在查看结果之后。预注册前探索只能标记为探索性，不得伪装成主报告依据。
16. If the source task triggers `成功与退出标准`, generalize the expert move: Make both success and failure criteria measurable so governance decisions do not depend on vague impressions. Rationale: 专家认为漂亮方案如果无法判断成败就不可治理。因此需要量化成功指标，例如模拟中系数恢复偏差小于 0.05、经验数据中 proxy 符号一致率大于 80%、复现包能在 1 小时内跑完主要结果；也要定义退出条件，例如年度维护超过 8 人月但服务项目少于 3 个，或连续 3 次评估无法给出可解释结论。
17. If the source task triggers `PLS术语治理`, generalize the expert move: Separate PLS-SEM, PCA, and two-stage proxy construction, and require implementation evidence for method labels. Rationale: 专家识别到会计研究者常把两阶段 proxy 构造误称为 PLS。正确处理是明确 PLS-SEM 是迭代估计测量模型和结构模型，PCA 是降维，两阶段聚合不是 PLS；平台应通过方法实现校验模块读取运行日志、配置和软件输出，发现标签与实际算法不匹配时阻断或强制标注为 approximation。
18. If the source task triggers `面板稳定性`, generalize the expert move: Extend the evaluation design beyond cross-sectional settings when the research context relies on panel data. Rationale: 会计研究中的 earnings quality、governance 等构念常跨多年使用，proxy 质量可能随时间漂移。专家要求加入年度 loading 稳定性、滚动窗口估计、构念漂移、within-firm 与 between-firm 变异比例等检查，否则平台只能服务横截面研究，适用范围不足。
19. If the source task triggers `方案组织`, generalize the expert move: Map the reasoning into a section structure that serves all audiences while preserving the governance logic. Rationale: 专家会将方案组织为执行摘要、问题背景、系统定位与职责边界、总体架构、潜变量建模策略、测量方法比较框架、验证与评估方法、PLS 治理、风险与控制、研究产出与审计、实施路线图、成本资源、成功标准与退出条件、结论。每一章都要回应至少一个关键角色的需求，并保持“方法评估与治理”的主线。
20. If the source task triggers `最终自检`, generalize the expert move: Perform a final expert check for overclaiming, unfair comparison, missing construct types, unresolved conflicts, and audit compliance. Rationale: 专家最后会检查方案是否暗示某种方法总是最好，是否遗漏形成式构念模拟，预注册是否留下探索期漏洞，指标筛选是否对所有方法公平，多方法冲突是否有终局规则，审计记录是否需要脱敏。只有这些点修正后，方案才不是漂亮空壳，而是经得起实际使用追问的治理基础设施设计。
21. If the source task triggers `任务定界`, generalize the expert move: 识别任务类型、交付物形态、受众范围和必须覆盖的结构约束。 Rationale: 专家会先多轮阅读题目，确认这不是代码实现或论文复现，而是一份面向量化研究负责人、研究员、数据工程、平台工程和风控的中文技术方案。交付物必须回答 6 个核心问题、包含 13 个二级章节、控制在约 3000-5000 字，并保存为指定 Markdown 文件。中间结论是先搭出完整章节框架，防止遗漏，再逐章填充并最终核对核心问题。
22. If the source task triggers `MVP 设定`, generalize the expert move: 为方案确定一个保守、可审计、成本可控的最小可行研究场景。 Rationale: 专家会判断高频数据成本高且处理复杂，不能一开始覆盖全市场、全历史和所有频率。合理 MVP 是流动性较好的股票池、5 分钟或 10 分钟 bar、至少 3 年历史样本、标准 RSJ 定义、简单但不可缺失的成本模型、基础回测和可复现报告。这个设定能覆盖不同市场环境，同时避免 tick 数据噪声过强或日频数据失去日内意义。
23. If the source task triggers `平台价值判断`, generalize the expert move: 明确为什么该任务需要平台化研究流程，而不是一次性脚本或单次回测。 Rationale: 专家会从高频数据特殊性、长期多参数验证、多人协作、可复现审计和研究生产一致性推导平台必要性。日内数据会遇到时区、早收盘、缺失 bar、停牌、复权和微观结构噪声，研究员若各自写脚本可能使用不同数据源、清洗规则和参数并得出矛盾结论。中间结论是方案要强调流程和治理大于单一 RSJ 结论，平台核心价值是标准化和留痕。
24. If the source task triggers `数据治理识别`, generalize the expert move: 系统列出高频数据治理风险，并说明每类风险若处理错误会如何污染因子结论。 Rationale: 专家会列出 UTC 与交易所本地时间、夏令时、正常交易时段、盘前盘后、午休、早收盘、缺失 bar、停牌、退市、除权除息、日频 reconciliation 和供应商版本等问题。特别会强调 A 股等市场的午休是连续交易窗口断点，午休前后价格不能直接连起来算收益率。中间结论是数据治理章节不能只写需注意，而要给出处理规则和错误后果。
25. If the source task triggers `因子定义与工程保护`, generalize the expert move: 给出可实现的因子定义，并把理论定义与生产研究保护规则分开说明。 Rationale: 专家会把论文启发部分限定为日内对数收益、RV、上半方差、下半方差和 RSJ=(Upside-Downside)/RV。随后加入生产工程保护：RV 极小或为 0 输出缺失而不是 0 或无穷；有效 bar 数不足、停牌、复权缺失或异常价格时输出缺失；极端收益 winsorize 或剔除要记录；周频或月频聚合只能使用当时可得数据；因子至少滞后一个交易周期。中间结论是第 6 章必须有精确公式和边界条件。
26. If the source task triggers `验证框架设计`, generalize the expert move: 设计防止过拟合的验证框架，并设置可量化的成功指标。 Rationale: 专家会拒绝只看样本内或 60 天短窗口，要求样本内、样本外和 6-12 个月前向纸面交易。验证要覆盖采样频率、持仓周期、聚合方式、市场环境、股票池和成本敏感性。具体门槛包括成本后年化 IR 大于 0.4、周换手小于 50%、参数秩相关大于 0.8、至少两个市场环境收益为正，并报告 0.5 倍、1 倍、2 倍成本假设。中间结论是没有量化门槛就无法判断是否值得生产。
27. If the source task triggers `风险控制闭环`, generalize the expert move: 把主要数据、统计、工程、交易和合规风险逐项映射到具体控制措施。 Rationale: 专家会把微观结构噪声、缺失 bar、时区日历错误、前视偏差、幸存者偏差、短样本过拟合、多重检验、成本低估、流动性不足、因子拥挤、供应商变更、研究生产不一致和合规授权列为关键风险。对应缓解包括跨频率比较、覆盖率阈值、统一日历服务、强制滞后、历史 universe、前向测试、记录失败实验、三层成本模型、ADV 约束、拥挤监控、版本锁定、共用代码与 CI，以及审查数据许可是否允许用于交易信号。
28. If the source task triggers `审计产出设计`, generalize the expert move: 规定每次实验必须输出的中间结果、配置、失败记录和复现材料。 Rationale: 专家会要求每次实验不仅输出最终绩效，还要保存因子定义、参数配置、数据版本、覆盖率和剔除统计、质量问题清单、中间因子值样本、组合持仓、换手率、绩效指标、失败实验、研究员解释、caveats、代码版本、容器镜像和配置。失败实验记录尤其重要，因为如果只记录成功结果，多重检验风险会被隐藏。
29. If the source task triggers `实施路线图`, generalize the expert move: 将平台建设拆成可停止、可评审的阶段，并说明每阶段是否允许影响真实交易。 Rationale: 专家会规划 6 个阶段：离线原型与数据审计、标准化计算与回测、稳健性成本统计检验、前向纸面交易、有限接入生产研究平台、真实模型评审。每阶段都要写目标、交付物、参与团队、成功标准和是否影响真实交易，并设置停止点，例如数据质量不达标或成本后收益为负则不进入下一阶段。中间结论是第 10 章应使用表格呈现，避免路线图变成空泛愿景。
30. If the source task triggers `资源协作估算`, generalize the expert move: 估算平台建设所需资源、相对成本和跨团队协作机制。 Rationale: 专家会给出相对资源量级而非精确预算：数据采购和存储成本为中到高，数据工程约 2-4 人月，量化研究约 2-3 人月，平台工程约 2-4 人月，风控合规约 0.5-1 人月，并说明长期维护需要持续投入。组织上需要联合评审机制，各角色签字或确认后才能推进到下一阶段。
31. If the source task triggers `成功与退出标准`, generalize the expert move: 定义继续推进、降级为辅助信号或停止投入的判断标准。 Rationale: 专家会把成功标准设为量化指标达成、数据审计通过、复现性验证通过和授权合规确认。退出条件包括数据质量问题无法解决、成本后收益在样本外消失、只有短窗口或少数参数有效、供应商变更后结论不可复现、研究生产不一致无法解决。还要说明 RSJ 在收益预测不稳定但能解释风险时可作为辅助信号，而不是直接进入投资模型。
32. If the source task triggers `摘要结论收束`, generalize the expert move: 让执行摘要和结论前后呼应，并明确建议、起点、风险和短回测限制。 Rationale: 专家会在执行摘要回答是否建议建设、MVP、主要价值、最大风险和短回测为何不足，在结论重申从离线审计开始、RSJ 只能先作为候选信号并需长期验证。两部分要前后保持一致：建议建设，但不是直接交易；起点是流动性股票池、5 分钟 bar、3 年历史；主要价值是可持续验证流程；最大风险是数据污染、过拟合和成本吞噬。
33. If the source task triggers `核心问题核对`, generalize the expert move: 逐一核对任务提出的核心问题是否都被方案中的相应章节回答。 Rationale: 专家会逐项检查 6 个核心问题：为什么需要专门平台应由第 2、3 章回答；高频数据额外风险由第 5、8 章回答；RSJ 验证步骤由第 6、7 章回答；如何避免偏差由第 5、6 章回答；如何判断稳定投资价值由第 7、12 章回答；分阶段规划由第 10 章回答。中间结论是全部有覆盖后才算完成任务。
34. If the source task triggers `角色覆盖核对`, generalize the expert move: 从每类目标受众视角复核方案是否回应其核心关注点。 Rationale: 专家会模拟五类角色阅读：研究负责人需要看到执行摘要、结论和成功指标；研究员需要看到因子流程、验证方法和实验灵活性；数据工程需要看到数据治理、质量阈值和版本管理；平台工程需要看到架构、可扩展性和维护成本；风控需要看到风险、控制措施和退出条件。中间结论是每类角色都应有自己的专属信息入口。
35. If the source task triggers `落地参数复核`, generalize the expert move: 检查方案中是否仍存在需要工程师自行猜测的参数、阈值或规则，并在合理范围内补足默认值。 Rationale: 专家会专门查找“可配置”“按样本校准”“需设定阈值”等留白，尽量补成可执行建议。原始经验中的具体默认值包括：最小方差阈值 epsilon 给出绝对下限 1e-8；winsorize 默认 0.5%，并要求报告 1% 敏感性；覆盖率阈值高流动性 95%、中流动性 90%、低流动性单独定义；插补默认禁止，仅限极少数场景且必须与未插补版本并列报告；熔断恢复后窗口重置，不足 30 分钟标记部分交易日。中间结论是方案要尽量自包含，让工程师不用再...
36. If the source task triggers `交付检查`, generalize the expert move: 完成最终格式、字数和保存路径检查，确保交付物符合任务要求。 Rationale: 专家会在写完后检查字数是否接近 3000-5000 字，若超出则精简重复或过细内容，若不足则补充必要示例和说明。最终交付应是一份专业但不冗余的 Markdown 技术方案，并保存到题目指定路径。
